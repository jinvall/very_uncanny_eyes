# Build Plan

## Phase 1 — Foundation and mode architecture

### Objectives

- Establish the rendering and behavior architecture needed for real mode switching.
- Formalize a mode/profile model that can support normal, dozing, suspicious, and angry states.
- Remove the ad hoc logic that has accumulated around the eye renderer and animation loop.

### Work items

1. Mode registry
   - Add explicit mode enum values and runtime selection path.
   - Map `normal`, `dozing`, `suspicious`, and `angry` to per-mode behavior profiles.
   - Keep the default mode stable while introducing future ones.

2. Expression state model
   - Create profile/state objects for:
     - eyelid state
     - blink timing
     - gaze drift
     - head motion
     - pupil response
   - Separate geometry, animation, and calibration concerns.

3. Rendering pipeline cleanup
   - Keep renderer logic deterministic and side-effect free.
   - Add dedicated render inputs: irisScale, gaze, lid state, expression blend, pupil shape.
   - Ensure smoke tests remain valid for each mode.

4. Asset discipline
   - Make an explicit rule: generated eye tables are generated artifacts, not hand-maintained code.
   - Preserve the large autogenerated files as output from a converter, not direct editing targets.
   - Record the conversion pipeline for future eye variants.

### Verification

- App starts in all defined modes.
- Dozing still behaves correctly after the refactor.
- No mode-specific logic leaks directly into the renderer.
- Build still succeeds with generated headers intact.

## Phase 2 — Realistic eye system and pupil math

### Objectives

- Move the project toward the target eye profile system: normalized eyeball + deterministic pupil centroid/radius mapping.
- Replace approximate logic with a realistic, measurable pupil model.
- Handle slitted and asymmetric pupils without causing the black pupil hole to render outside the actual pupil.

### Work items

1. Eye-profile abstraction
   - Introduce an eye profile system with iris type, pupil type, expression type, and realism settings.
   - Keep a baseline mammalian/pupil profile and additional animal variants.

2. Deterministic pupil mapping
   - Build the normalized 200x200 eyeball asset pipeline.
   - Use a crosshair-based pupil detection strategy that is valid for cat/reptilian/goat-like pupils.
   - Measure pupil center and radius from the normalized black marker rather than using a dot.

3. Dilation tightening
   - Replace the raw ADC-to-pupil mapping with a physiological response model:
     - light-to-pupil conversion
     - constriction timing
     - dilation timing
     - deadband / smoothing / hysteresis
   - Keep ambient adaptation and autonomous iris motion as separate concerns.

4. Non-round pupil validation
   - Model pupil shape as radial or elongated based on profile.
   - Validate slit-pupil rendering against a fixed 200x200 reference image.
   - Include guard checks for edge conditions when the pupil narrows at its smallest diameter.

5. Eye asset generation
   - Create a generator or conversion script that consumes source art and produces the final dataset.
   - Ensure the generated output remains manageable despite large per-variant tables.

### Verification

- Deterministic pupil center and radius values remain stable for fixed inputs.
- Slitted pupil never escapes the iris boundary.
- LDR adaptation is smoother and more realistic than the current direct mapping.
- A selected eye profile produces the expected visual output without toggling code paths manually.

## Phase 3 — Display, streaming, and operator polish

### Objectives

- Support a clean remote-display deployment with minimal light spill.
- Let the operator switch modes and calibration values in a stable UI.
- Make the system production-friendly and testable in real deployment conditions.

### Work items

1. 16:9 borderless display mode
   - Keep the window borderless and fixed to remote-display-friendly proportions.
   - Remove unnecessary UI chrome or desktop leakage.

2. RTSP and VLC verification
   - Re-test the remote capture path with the new display layout.
   - Confirm the stream remains stable even when the local app restarts or re-creates the window.

3. TUI and runtime controls
   - Add direct mode selection and tuning controls to the TUI.
   - Expose LDR calibration points and pupil response tuning without editing source.

4. Expression tuning and calibration
   - Add a calibration layer for ambient light, pupil response, and expression strength.
   - Provide runtime adjustments for suspicious and angry profiles.

5. Deployment hardening
   - Validate startup, restart, and mode-change flows.
   - Confirm the system works from a clean environment.

### Verification

- The display stays at 16:9 borderless output.
- VLC consistently connects to the RTSP stream.
- TUI can launch and switch modes without manual restarts.
- Light and pupil curves behave acceptably across typical room lighting conditions.

---

## Execution strategy

### Dependency order

1. Finish the mode architecture before introducing new expression behaviors.
2. Finish the realistic eye math before changing generated assets heavily.
3. Finish polishing the display and launch experience after the eye system is stable.

### Acceptance rule

No phase is considered complete until the implementation passes smoke tests, real-time visual checks, and a targeted validation pass for the exact feature introduced in that phase.

### Constraint

Because each generated eye table is extremely large, this work should be generator-driven and kept away from manual editing of generated output whenever possible.
